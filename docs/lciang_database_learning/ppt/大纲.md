## Page 2：RUCBase 系统架构总览
- **架构分层图（自底向上）**：
  - **磁盘与存储层**：DiskManager（文件IO，基于 POSIX 的 read/write/lseek/open/close/unlink）-> BufferPoolManager（内存缓存，Page 为 4096B，Frame 为缓冲池槽位，page_table_ 做 PageId→frame_id 映射）-> RM（记录管理/堆文件，页 0 为文件头 RmFileHdr，数据页从页 1 开始，页内 bitmap 管理槽位分配）
  - **索引层**：IxIndexHandle（B+树，内部结点存 key→child_page，叶子结点存 key→rid 列表，叶子间双向链表相连），依赖存储层提供页面读写
  - **执行层**：火山模型算子（SeqScan / Projection / NestedLoopJoin / Insert / Delete / Update / Sort / IndexScan），每个算子实现 init() + next() 接口，pull-based 行式迭代
  - **并发控制层**：LockManager（行锁 S/X + 表锁 S/X/IS/IX + 多粒度层次 + 兼容矩阵判断）+ TransactionManager（DEFAULT→GROWING→COMMITTED/ABORTED 状态机，WriteSet 回滚），贯穿于执行层和存储层接口
- **数据流说明**：SQL语句（Parser→Analyzer→Optimizer） -> 执行引擎（算子树，叶子=扫描，内部=连接/投影/排序） -> 访问方法（堆文件 RmFileHandle / B+树 IxIndexHandle） -> 缓冲池 BufferPoolManager（page_table 映射 + LRU 淘汰） -> 磁盘 DiskManager（lseek + read/write）

## Page 5：关键原理 — 存储与页面
- **页面抽象**：Page（4096B）→ Frame（缓冲池槽位，含 page 指针、pin_count、is_dirty、frame_id）→ BufferPool（固定数量 frame 数组 + page_table_ 哈希映射 + free_list_ 空闲链表）
- **页面布局**：每个 Page 内部 [4B LSN（日志序列号）][PageHdr][payload...]，OFFSET_PAGE_HDR = 4，实际数据从偏移 4 字节开始
- **页面生命周期**：new_page（分配新页号 → 从 free_list_ 取或 victim() 淘汰 → 写入缓冲池 → pin_count=1 标记被引用）→ fetch_page（查 page_table_，命中直接返回并 pin_count++ → 未命中则从磁盘 read_page 再放入，复用上述淘汰逻辑）→ unpin_page（pin_count--，若 is_dirty=true 则标记脏页 → 当 pin_count==0 时调用 replacer.unpin 将 frame 加入 LRU 链表使其可淘汰）→ flush_page（若 is_dirty=true，调用 disk_manager.write_page 回写磁盘 → is_dirty=false）→ delete_page（pin_count 必须为 0 → 从 page_table_ 移除 → 释放 frame → 加入 free_list_）
- **持久化**：POSIX I/O（open 获取 fd → lseek 定位到 page_no × PAGE_SIZE → read/write 整页 4096B → close 释放 fd → unlink 删除文件）
- **PageId 结构**：{fd（文件描述符）, page_no（页号）} 二元组，用于 page_table_ 映射

## Page 6：关键原理 — 替换策略（LRU）
- **LRU 思想**：最近最少使用页优先淘汰，利用时间局部性原理——最近被访问的页更可能再次被访问
- **数据结构**：双向链表（std::list<frame_id_t>）维护访问顺序（队头=最近使用，队尾=最久未使用）+ unordered_map<frame_id_t, iterator> 实现 O(1) 查找和删除
- **核心操作**：
  - `victim()` → 返回最久未使用的 frame_id：从链表尾部 pop_back，从 map 中移除对应条目，加 mutex 保证线程安全
  - `pin(frame_id)` → 固定 frame，使其不可淘汰：从链表中删除对应结点（通过 map O(1) 定位），从 map 中移除；该 frame 被某个线程引用中，pin_count > 0
  - `unpin(frame_id)` → 释放 frame，使之可淘汰：将 frame_id 插入链表头部（标记为最近使用），加入 map；此时 pin_count == 0，frame 回到 LRU 候选池
- **并发控制**：使用 `std::mutex latch_` 保护链表与 map 的所有操作（victim/pin/unpin 各自加 `std::scoped_lock`），避免多线程同时修改导致链表断裂或 map 不一致
- **与 BufferPool 协作**：fetch_page 找不到空闲 frame 时调用 victim() 获取淘汰目标 → BPM 判断该 frame 是否 is_dirty → 若脏则先 write_page 回写磁盘 → 再分配给新 page 使用

## Page 7：关键原理 — 缓冲池管理器
- **职责**：页面缓存（减少磁盘 I/O）、页表映射（PageId → frame_id 快速定位）、替换协作（调用 Replacer 淘汰旧页）、脏页回写（保证持久性）
- **核心数据结构**：
  - `Frame pages_[pool_size]`：固定大小 frame 数组，每个 Frame 含 `Page*`（实际 4096B 数据）、`pin_count_`（引用计数）、`is_dirty_`（脏标记）、`frame_id_`、`reset_memory()`（清零方法）
  - `page_table_`：unordered_map<PageId, frame_id_t>，O(1) 查找页面是否在缓冲池中
  - `free_list_`：std::list<frame_id_t>，存放完全空闲的 frame（pin_count==0 且未被 LRU 追踪），优先从此分配
  - `replacer_`：LRUReplacer 实例，管理 pin_count==0 的可淘汰 frame
- **核心算法流程**：
  - `fetch_page(page_id)`：
    1. 加 `std::scoped_lock{latch_}` 保护整个操作
    2. 查 page_table_：若命中 → pin_count++ → 调 replacer_.pin(frame_id) 移出 LRU → 返回 Page*
    3. 若未命中：从 free_list_ 取空闲 frame → 若 free_list_ 为空则调 replacer_.victim() 获取淘汰 frame → 若该 frame 的 is_dirty 为真，先 disk_manager_.write_page() 回写磁盘 → 从 page_table_ 移除旧 page 映射 → disk_manager_.read_page() 读取目标 page → 更新 page_table_ → reset_memory 清零 → pin_count=1 → 返回 Page*
  - `new_page(page_id)`：类似 fetch_page 但跳过 read_page，直接清零后返回
  - `unpin_page(page_id, is_dirty)`：找到 frame → 若 is_dirty 则设置 is_dirty_=true → pin_count-- → 若 pin_count==0 则 replacer_.unpin(frame_id) 加入 LRU 链表
  - `delete_page(page_id)`：要求 pin_count==0 → 从 page_table_ 移除 → frame 加入 free_list_ → disk_manager_.deallocate_page()
- **一致性保证**：脏页淘汰前必须先 write_page 回写磁盘 → 保证 ACID 的 D（持久性）；pin_count > 0 的 page 不在 LRU 链表中 → 保证正在使用的页面不会被淘汰 → 避免 use-after-free

## Page 8：关键原理 — 记录管理（Heap + Bitmap）
- **文件布局**：页 0 为文件头（RmFileHdr），存储 record_size、num_records_per_page、num_pages、first_free_page_no、bitmap_size 等元数据；数据页从页 1 开始
- **页内布局**：每个数据页 = [RmPageHdr（next_free_page_no + num_records）][bitmap（record 占用位图，1=占用/0=空闲）][slot 0][slot 1]...[slot N-1]，每条记录固定大小 = record_size
- **bitmap 位图管理**：`Bitmap::set(bitmap, slot_no)` 标记槽位已占用；`Bitmap::reset(bitmap, slot_no)` 标记槽位空闲；`Bitmap::is_set(bitmap, slot_no)` 查询槽位状态；`Bitmap::first_bit(false, bitmap, count)` 查找第一个空闲槽位
- **空闲页链表**：
  - `file_hdr_.first_free_page_no` 指向第一个有空闲槽位的页
  - 每个数据页的 `page_hdr->next_free_page_no` 指向下一个有空闲槽位的页
  - 插入流程：create_page_handle() 优先从 first_free_page_no 获取空闲页 → 若为 RM_NO_PAGE（无空闲页）则 create_new_page_handle() 创建新页 → 在 bitmap 中找空闲 slot → 写入数据
  - 回收流程：当页面从满变为不满（num_records 从 num_records_per_page 减到 num_records_per_page-1）时，release_page_handle() 将该页插入空闲链表头部
- **RmScan 扫描器**：初始化时获取 RmFileHandle 引用 → 从页 1 开始遍历所有数据页 → 每页通过 bitmap 遍历所有有效 slot → next() 移动到下一条记录 → is_end() 判断是否扫描完所有页 → rid() 返回当前记录的 Rid{page_no, slot_no}

## Page 9：关键原理 — B+ 树索引
- **B+ 树结构**：内部结点存索引（分隔键 key → 孩子页号 child_page），第 i 个 key 是第 i+1 个子树的最小值；叶子结点存数据（key → rid 列表，支持重复键时多个 rid）；叶子间通过双向链表（prev_leaf / next_leaf）相连，支持范围扫描
- **唯一索引约束**：不存储重复键值，插入前需在叶子结点中查重（lower_bound / upper_bound），若 key 已存在则拒绝插入
- **核心操作流程**：
  - **查找（get_value / find_leaf_page）**：从根结点开始，在内部结点通过二分查找（lower_bound）定位包含目标 key 的孩子页号 → 递归到叶子 → 在叶子中二分查找具体 key → 返回 rid 列表
  - **插入（insert_entry）**：find_leaf_page 定位目标叶子 → 调用 leaf_insert 插入键值对 → 若叶子结点已满（>= max_size），调用 split() 将结点分裂为两个（均分 key），取新结点的最小 key 作为分隔键 → insert_into_parent() 将分隔键+新结点页号插入父结点 → 父结点可能同样溢出，递归上溢 → 若最终根结点也溢出，创建新根（树高度 +1）
  - **删除（delete_entry）**：find_leaf_page 定位目标叶子 → 调用 leaf_remove 删除键值对 → 若结点不足半满（< min_size），优先 redistribute（从相邻兄弟结点借一个 key，更新父子分隔键）→ 若兄弟也不足半满则 coalesce（与兄弟合并，删除父结点对应分隔键）→ 递归调整父结点 → 若根结点被删到只剩一个孩子，删除旧根，孩子成为新根（树高度 -1）
- **并发控制**：
  - 粗粒度：`std::scoped_lock{root_latch_}` 锁整棵树，所有操作串行化，实现简单但并发度低
  - 蟹行协议（Crabbing Protocol）：find_leaf_page 过程中自上而下加锁（先锁父 → 获取孩子 → 锁孩子 → 读操作立即释放父锁；写操作判断孩子是否"安全"——即操作后不会上溢/下溢传播——若安全则释放祖先锁，否则保留）。所有锁存入 page_set_ (std::unordered_set<Page*>)，操作完成后 unlock_all_pages() 统一释放

## Page 10：已完成模块与接口 — 缓冲池管理器模块
- **DiskManager**：文件操作（create_file / open_file / close_file / destroy_file）、页面读写（write_page 将 4096B 数据 lseek + write 到磁盘 / read_page 将 4096B 数据 lseek + read 到内存）、页面分配（allocate_page 扩展文件大小，返回新页号）
  - 关键细节：open_file 前需 `is_file(path)` 判断文件是否存在，不存在应抛 FileNotFoundError（测试期望此异常类型）；write_page/read_page 使用 `lseek(fd, page_no * PAGE_SIZE, SEEK_SET)` 定位
- **Replacer（LRU）**：victim() 淘汰 frame 返回 frame_id_t / pin(frame_id) 移出链表 / unpin(frame_id) 加入链表头部；内部使用 `std::list<frame_id_t>` + `std::unordered_map<frame_id_t, list::iterator>` + `std::mutex latch_`
  - 关键细节：pin() 操作即使 frame_id 不在链表中也不报错（可能已被 pin），unpin() 需检查 frame 是否已在链表中避免重复插入
- **BufferPoolManager**：new_page(page_id) 分配新页 / fetch_page(page_id) 获取页面 / unpin_page(page_id, is_dirty) 释放引用 / delete_page(page_id) 删除页面 / flush_page(page_id) 和 flush_all_pages() 回写脏页
  - 关键细节：new_page 调用 disk_manager_.allocate_page() 获取新页号并写入 page_id.page_no；fetch_page 时若 page 不在缓冲池中，需先确保有空闲 frame（free_list_ 或 victim），若淘汰的 frame 是脏页则先回写；所有公开方法加 `std::scoped_lock{latch_}`

## Page 11：已完成模块与接口 — 记录管理器模块
- **RMFileHandle 辅助函数**：
  - `create_new_page_handle()`：调用 buffer_pool_manager_->new_page() 分配新页 → 初始化 page_hdr（next_free_page_no = RM_NO_PAGE, num_records = 0）→ Bitmap::init 初始化 bitmap（全部清零）→ file_hdr_.num_pages++ → 返回 RmPageHandle
  - `fetch_page_handle(page_no)`：调用 buffer_pool_manager_->fetch_page() 获取 Page* → 若 page_no 无效（Page* == nullptr）抛 PageNotExistError → 返回 RmPageHandle(&file_hdr_, page)
  - `create_page_handle()`：若 file_hdr_.first_free_page_no != RM_NO_PAGE，fetch 该空闲页 → 否则调用 create_new_page_handle() 创建新页
  - `release_page_handle(page_handle)`：页面从满变未满时 → page_hdr.next_free_page_no = file_hdr_.first_free_page_no → file_hdr_.first_free_page_no = 当前 page_no，插入空闲链表头部
- **RMFileHandle 记录操作**：
  - `get_record(rid)`：fetch_page_handle(rid.page_no) → Bitmap::is_set 检查 slot 是否有效（无效抛 RecordNotFoundError）→ memcpy 复制 slot 数据到 RmRecord → 返回 unique_ptr<RmRecord>；加行级 S 锁保护读操作
  - `insert_record(buf)`：create_page_handle() 获取空闲页 → Bitmap::first_bit(false, ...) 找空闲 slot → memcpy 写入数据 → Bitmap::set 标记占用 → num_records++ → 若页面变满则更新 first_free_page_no → 返回 Rid{page_no, slot_no}；加行级 X 锁保护新记录
  - `delete_record(rid)`：fetch_page_handle(rid.page_no) → Bitmap::reset 标记空闲 → num_records-- → 若页面从满变未满则 release_page_handle → 加行级 X 锁
  - `update_record(rid, buf)`：fetch_page_handle(rid.page_no) → memcpy 覆盖 slot 数据 → 加行级 X 锁
- **RMScan 迭代器**：构造函数初始化 rid_{fd, 1, -1} → next() 遍历 page_no 和 slot_no，通过 bitmap 跳过空闲槽位 → is_end() 判断是否超出最后一页 → rid() 返回当前 Rid

## Page 12：已完成模块与接口 — B+ 树索引模块
- **IxNodeHandle（结点内操作）**：
  - `lower_bound(key)`：二分查找，返回第一个 >= key 的位置（用于内部结点定位子树）
  - `upper_bound(key)`：二分查找，返回第一个 > key 的位置（用于确定 key 在结点中的范围）
  - `leaf_lookup(key)`：在叶子结点中二分查找 key，返回位置（未找到返回 -1）
  - `internal_lookup(key)`：在内部结点中二分查找，返回包含 key 的孩子页号；注意当 idx==0 时直接返回 value_at(0)（首个 key 是最小值，所有 < key[0] 的 key 都在第一个子树中）
  - `insert_pairs(start, pairs, count)`：在指定位置批量插入键值对，后续元素后移
  - `insert(key, value)`：找到正确位置并插入单个键值对
  - `erase_pair(pos)`：删除指定位置的键值对
  - `remove(pos)`：删除指定位置的 key（内部结点用）
- **IxIndexHandle（整树操作）**：
  - **查找**：`find_leaf_page(key)` 从根遍历到叶子结点，返回叶子 Page*；`get_value(key)` 调用 find_leaf_page + leaf_lookup，返回 rid 列表
  - **插入**：`insert_entry(key, rid)` → 找到叶子 → 插入 → 若结点满则 `split()` 创建新结点并均分键值对 → `insert_into_parent()` 将分隔键递归插入父结点 → 若创建新根则更新 root_page_
  - **删除**：`delete_entry(key, rid)` → 找到叶子 → 删除 → 若不足半满则 `coalesce()`（合并兄弟）或 `redistribute()`（从兄弟借）→ `adjust_root()` 检查根是否需要降高度
  - **并发**：`find_leaf_page` 实现蟹行协议（自上而下加页级 mutex 锁）→ page_set_ 存放所有持有的锁 → `unlock_all_pages()` 统一释放 → 插入/删除操作调用 `maintain_parent(leaf)` 在修改叶子第一个 key 后同步更新父结点分隔键（否则 check_tree 断言失败）

## Page 13：缓冲池实现要点
- **页面定位**：根据 (fd, page_no) 计算磁盘偏移 = page_no × PAGE_SIZE，调用 `lseek(fd, offset, SEEK_SET)` 定位文件指针，然后 `read(fd, buf, PAGE_SIZE)` / `write(fd, buf, PAGE_SIZE)` 读写整页 4096B
- **淘汰时脏页判断**：调用 replacer_.victim() 获得淘汰目标 frame_id → 检查 `pages_[frame_id].is_dirty_` 标志 → 若为 true，先调用 `disk_manager_.write_page(fd, page_no, page->data_)` 将脏数据回写磁盘 → 再从 `page_table_` 中移除旧 PageId 映射 → 此时 frame 才可安全分配给新页面使用。若跳过脏页回写 → 数据丢失 → 持久性被破坏
- **引用计数机制**：`pin_count` 记录当前有多少线程/操作正在使用该 page。fetch_page/new_page 时 pin_count++ → 表示"正在使用中"；unpin_page 时 pin_count-- → 表示"使用完毕"；当 pin_count == 0 时，调用 `replacer_.unpin(frame_id)` 将 frame 加入 LRU 链表，使其进入可淘汰候选池。多个线程可同时 pin 同一页面（如读-读并发），pin_count 会 > 1，直到最后一个线程 unpin 才进入 LRU。delete_page 必须检查 pin_count == 0（无人在用），否则抛异常
- **并发控制**：粗粒度 mutex（`std::mutex latch_`）锁整个缓冲池，所有公开方法入口加 `std::scoped_lock lock{latch_}`。这样实现简单、正确性容易保证，缺点是并发度低（同一时刻只有一个线程访问缓冲池），可后续优化为更细粒度的页级锁或分区锁
- **free_list_ 优先策略**：fetch_page 需要空闲 frame 时，先检查 free_list_ 是否有空闲 frame → 有则直接取出使用（这些 frame 没有 pin_count、没有关联数据，最干净）→ free_list_ 为空时才调用 replacer_.victim()（可能触发脏页回写，开销大）。这种分层策略最小化了淘汰开销

## Page 14：B+ 树实现要点
- **结点第一个 key 的特殊作用**：每个内部结点的第 i 个 key 等于第 i+1 个子树的最小 key（"分隔键"语义）。当叶子结点的第一个 key 被修改（在位置 0 插入新 key 或删除位置 0 的 key）时，必须调用 `maintain_parent(leaf)` 递归向上更新所有祖先结点中对应的分隔键。若遗漏 → 父结点分隔键与实际子树最小 key 不一致 → `check_tree` 自检断言失败
- **插入流程详解**：
  1. `find_leaf_page(key)`：从 root 遍历到叶子，蟹行协议加锁
  2. 叶子 `insert_pairs()` / `insert()`：二分找到位置，插入 (key, rid)
  3. 若叶子 `node_size > max_size`：调用 `split()` — 创建新叶子结点，将原叶子后半部分 key 移动到新叶子，更新新叶子的 prev_leaf/next_leaf 指针维护链表
  4. `insert_into_parent(old_node, new_key, new_node)`：将 (new_key=新结点的最小key, new_node=新结点页号) 插入父结点 → 若父结点也满，继续 split + insert_into_parent 递归上溢
  5. 若递归到根且根也满：创建新根结点 — 旧根分裂为两个结点，新根包含两个分隔键指向两个孩子 — `update_root_page_no(new_root_page_no)` — 树高度 +1
  - 注意：`create_node()` 返回的新页其 page_hdr.parent 被 BufferPoolManager::reset_memory 清零为 0，而 `INVALID_PAGE_ID = -1`，`is_root_page()` 判断 `parent == INVALID_PAGE_ID` → 新根需显式调用 `set_parent_page_no(IX_NO_PAGE)` 修正
- **删除流程详解**：
  1. `find_leaf_page(key)`：定位目标叶子
  2. 叶子 `remove()`：删除键值对
  3. 若叶子 `node_size < min_size`：尝试 `redistribute()` — 从相邻兄弟借一个 key。将兄弟的一个 key 移到当前结点 → 更新父结点对应分隔键为新兄弟的最小 key
  4. 若兄弟也 `<= min_size`（不够借）：`coalesce()` — 将当前结点的所有 key 移到兄弟结点 → 删除当前结点 → 从父结点删除对应的分隔键 → `adjust_root()` 检查根是否只剩一个孩子（若是，删除旧根，孩子成为新根，树高度 -1）
  5. 递归向上：`adjust_root` 返回 false 时需手动 unpin root page（否则 pin 泄漏 → 缓冲池耗尽 → 后续操作卡死）
- **并发设计决策**：采用蟹行协议（细粒度页级锁），读操作：find_leaf_page 加锁后，获取孩子 → 锁孩子 → 立即释放父亲；写操作：find_leaf_page 加锁后，获取孩子 → 锁孩子 → 判断孩子是否"安全"（孩子操作不会导致上溢/下溢传播）→ 安全则释放所有祖先锁，否则保留 → 最终 unlock_all_pages() 统一释放残留锁。与粗粒度锁（整树互斥）相比，蟹行协议在写操作中允许并发读，提升了并发度

## Page 15：关键原理 — 火山模型与算子树（Lab3）
- **火山模型（Iterator Model / Volcano Model）**：每个查询算子实现统一的迭代器接口——`init()` 初始化内部状态 + `next()` 返回下一条记录（或 nullptr 表示 EOF）。上层算子通过调用下层算子的 `next()` 逐行拉取数据（pull-based 模型），形成自顶向下的调用链
- **核心接口**：
  - `void init()` — 初始化算子状态，递归调用子算子的 init()。对于需要重置的算子（如 NLJ 内层），每次循环前重新 init
  - `std::unique_ptr<RmRecord> next()` — 返回下一条符合条件的数据记录，数据耗尽返回 nullptr
- **算子树结构**：
  - **叶子结点（数据源）**：SeqScan（通过 RmScan 迭代器遍历堆文件）、IndexScan（通过 IxScan 迭代器遍历 B+ 树叶子链表，按 key 升序输出）
  - **一元内部结点（流式变换）**：Projection（投影指定列，构造只含目标列的新记录）、Sort（全量收集到内存，std::sort 排序后输出）
  - **二元内部结点（连接）**：NestedLoopJoin（外层左子结点逐行 → 内层右子结点全量扫描 → 匹配 join 条件 → 拼接左右记录输出）
- **数据流向示例**：`SELECT a, c FROM T1 JOIN T2 ON T1.b=T2.b ORDER BY a` → Sort ← Projection ← NLJ(左=SeqScan(T1), 右=SeqScan(T2))
- **AbstructExecutor 基类**：所有算子的父类，定义 `init()` 和 `next()` 纯虚函数；持有 `Context*` 上下文指针（含事务、锁管理器引用）

## Page 16：关键原理 — 连接算法与排序（Lab3）
- **Nested Loop Join（NLJ）**：
  - 算法：外层（左子结点）逐行获取记录 L → 内层（右子结点）init() 后逐行获取记录 R → 检查 join 条件（L.col == R.col）→ 匹配则拼接 L+R 所有列生成新记录并返回
  - 时间复杂度 O(M × N)，其中 M=左表行数、N=右表行数。实现上每次外层循环需 `right_child_->init()` 重置右表迭代器，使其重新从头扫描
  - 优化方向：小表放外层减少 init 次数；可改进为 Block NLJ（将外层批量读入内存减少磁盘 I/O）或 Index NLJ（内层走索引替代全表扫描）
- **Sort（排序算子）**：
  - 全量物化策略：在 init() 中循环调用 `child_->next()`，将所有记录收集到 `std::vector<RmRecord>` → 使用 `std::sort` + 自定义比较函数（按 sort_cols 依次比较）→ 排序后按序输出
  - 特点：非流式（需全部数据就绪后才能输出第一条），内存占用 O(N)；适用于 ORDER BY 子句
- **IndexScan（索引扫描）**：
  - 通过 `IxScan` 迭代器遍历 B+ 树叶子结点链表（利用叶子的 next_leaf 指针），从第一个叶子开始按页扫描所有 key→rid 对
  - 优势：利用 B+ 树的有序性，天然按索引 key 升序输出；可配合范围条件（lower_bound + upper_bound）实现高效范围扫描

## Page 18：查询执行器实现要点（Lab3）
- **写操作需同步索引**：Insert / Delete / Update 不仅操作记录层（RmFileHandle），还必须对所有关联该表的索引（通过 `sm_manager_->get_indexes(tab_name)` 获取索引列表）调用对应的 `insert_entry()` 或 `delete_entry()`。若遗漏 → 索引与数据不一致 → 后续通过索引查询会返回错误结果
- **Update ≠ 原地更新**：UpdateExecutor 的实现是 Delete + Insert，而非直接 memcpy 覆盖原槽位。原因：新记录大小可能变化（虽然当前 RUCBase 是定长记录，但框架预留了扩展空间），且 delete+insert 保证索引正确更新（先删旧 key→rid 映射，再插新 key→rid 映射）
- **NLJ 内层需每次 init()**：外层每取一行，内层必须重新调用 `right_child_->init()` 将右表迭代器重置到起始位置。若忘记 init → 第二次外循环时右表已到 EOF → 后续所有外行都无法匹配 → join 结果错误
- **Sort 全量物化**：在 init() 阶段将所有记录读入 vector<RmRecord> → std::sort 排序 → next() 依次返回。非流式处理意味着大数据量时内存压力大，但实现简单且与火山模型兼容
- **DDL drop_table 需先删索引**：drop_table 时必须先调用 `drop_index()` 删除该表所有关联索引（清理索引文件），再删除表文件本身。若顺序颠倒 → 索引文件残留
- **元数据持久化**：所有 DDL 操作通过读写 .db.meta 文件维护数据库元数据（表定义、列信息、索引信息），关闭数据库后元数据不丢失

## Page 19：关键原理 — 两阶段封锁（2PL）（Lab4）
- **2PL 定义**：事务的执行分为两个阶段 —— GROWING 阶段（只获取锁，不释放任何锁）和 SHRINKING 阶段（只释放锁，不获取新锁）
- **严格 2PL（Strict 2PL）**：SHRINKING 阶段推迟到事务提交（commit）或回滚（abort）时，一次性批量释放所有持有的锁。这是 RUCBase 采用的策略，能保证级联回滚（Cascading Abort）不发生
- **事务状态机**：
  - `DEFAULT`：事务对象刚创建，尚未开始
  - `begin()` → `GROWING`：事务进入执行阶段，可以获取锁、执行读写操作
  - `commit()` → `COMMITTED`：持久化 WAL 日志 → 释放所有锁（遍历 lock_set_ 调用 unlock）→ 写操作生效
  - `abort()` → `ABORTED`：逆序遍历 write_set_ 回滚写操作 → 释放所有锁 → 写操作撤销
- **状态转换规则**：
  - DEFAULT → GROWING：调用 begin()，分配唯一 txn_id
  - GROWING → COMMITTED：调用 commit()，前提是事务处于 GROWING 状态
  - GROWING → ABORTED：调用 abort()，或执行过程中抛出 TransactionAbortException（锁冲突）
  - COMMITTED / ABORTED 是终态，不可再转换
- **2PL 保证的隔离性**：通过 GROWING 阶段不释放锁，保证了锁的持有时间覆盖整个读写操作窗口，避免幻读/不可重复读/脏读等并发异常

## Page 20：关键原理 — 多粒度封锁与死锁预防（Lab4）
- **锁粒度层次**：数据库系统支持多粒度锁 —— 表级锁（TABLE，粗粒度，锁定整张表）和行级锁（RECORD，细粒度，锁定单条记录）。在加行级锁之前，必须先获取对应表的意向锁（Intention Lock），形成层次保护
- **锁类型**：
  - 行级：S（Shared，读锁）/ X（Exclusive，写锁）
  - 表级：IS（Intention Shared，打算加行 S）/ IX（Intention Exclusive，打算加行 X）/ S（表级读锁，等价于对所有行加 S）/ X（表级写锁，等价于对所有行加 X）/ SIX（S + IX，表读 + 行写）
- **锁兼容矩阵**（✓=兼容，✗=冲突→Abort）：

|       | NL | IS | IX | S  | SIX | X  |
|-------|----|----|----|----|-----|----|
| **NL** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **IS**  | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |
| **IX**  | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |
| **S**   | ✓ | ✓ | ✗ | ✓ | ✗ | ✗ |
| **SIX** | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ |
| **X**   | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |

- **No-Wait 死锁预防**：当锁请求与当前 group_lock_mode_ 不兼容时，不等待、不重试，立即抛出 `TransactionAbortException(txn_id, DEADLOCK_PREVENTION)`。这种策略避免了死锁（因为不等待就不会产生循环等待），代价是可能 abort 掉本可以等待后成功的事务
- **锁升级（Lock Upgrade）**：事务可以先获取 S 锁，后续需要写入时升级为 X 锁。升级过程中必须检查是否有其他事务持有该资源的 granted 锁 —— 若有则 abort（两个事务同时从 S 升级到 X 会导致写保护失效）
- **WriteSet 回滚机制**：
  - 写操作执行前记录 `WriteRecord`：INSERT_TUPLE（记录插入的 rid）/ DELETE_TUPLE（记录被删记录的原始数据 + rid）/ UPDATE_TUPLE
  - abort() 时**逆序**遍历 write_set_（后执行的先撤销），根据类型反向操作：
    - INSERT_TUPLE → `fh->delete_record(rid)` 删除插入的记录
    - DELETE_TUPLE → `fh->insert_record(rid, old_data)` 恢复到原 rid
    - UPDATE_TUPLE → delete_record(new_rid) + insert_record(old_rid, old_data)
  - 逆序保证：若先插入后删除同一条记录，回滚时先撤销删除、再撤销插入，逻辑一致

## Page 21：已完成模块与接口 — 锁管理器（Lab4）
- **7 个上锁接口**（每个均加 `std::scoped_lock{latch_}` 保护内部数据结构）：
  - `lock_shared_on_record(txn, rid, tab_fd)` — 行级 S 锁：检查兼容性（兼容 NL/IS/IX/S，冲突 X/SIX）→ 创建 LockRequest(LockMode::SHARED, granted=true) → 更新 group_lock_mode_ = S → 插入 txn->lock_set_
  - `lock_exclusive_on_record(txn, rid, tab_fd)` — 行级 X 锁：先在队列中查找是否已有该 txn 的 granted 锁 → 若有则检查其他 txn 的 granted 锁（有则 abort，实现锁升级冲突检测）→ 将已有 S 锁升级为 X → 若没有旧锁则检查兼容性（只兼容 NL，其他均冲突）→ 创建 LockRequest(LockMode::EXCLUSIVE, granted=true) → group_lock_mode_ = X → 插入 lock_set_
  - `lock_shared_on_table(txn, tab_fd)` — 表级 S 锁：兼容 NL/IS/IX/S，冲突 X/SIX → 若原为 NL 或 IS 则升级为 S
  - `lock_exclusive_on_table(txn, tab_fd)` — 表级 X 锁：兼容 NL，冲突所有其他 → 支持 IS/IX/S→X 升级（升级前检查其他 txn 的 granted 锁）
  - `lock_IS_on_table(txn, tab_fd)` — 表级 IS 锁：兼容 NL/IS/IX/S，冲突 X/SIX → 若原为 NL 则升级为 IS
  - `lock_IX_on_table(txn, tab_fd)` — 表级 IX 锁：兼容 NL/IS/IX，冲突 S/SIX/X → 若原为 NL 或 IS 则升级为 IX
- **解锁接口**：
  - `unlock(txn, lock_data_id)` — 查找 lock_table_[lock_data_id] → 在 request_queue_ 中移除该 txn 的请求 → 遍历剩余 granted 请求重算 group_lock_mode_（取所有 granted 锁的"最大"模式）→ 从 txn->lock_set_ 中 erase → 若队列为空，可选择清理 lock_table_ 条目
- **内部数据结构**：
  - `lock_table_`：`std::unordered_map<LockDataId, LockRequestQueue>`，全局锁表
  - `LockDataId`：{tab_fd, rid 或 page_no, data_type (TABLE/RECORD)} 三元组，唯一标识一个可加锁资源
  - `LockRequestQueue`：含 `std::list<LockRequest> request_queue_`（请求列表）+ `GroupLockMode group_lock_mode_`（当前组锁模式，等于所有 granted 锁的最大模式）
  - `LockRequest`：{txn_id, LockMode, granted_} 三元组
  - `std::mutex latch_`：全局互斥锁，保护整个 lock_table_

## Page 22：已完成模块与接口 — 事务管理器（Lab4）
- **TransactionManager**：
  - `begin(txn, isolation_level)` — 分配新 txn_id（自增计数器）→ 设置 txn->state_ = GROWING → 将 {txn_id, txn} 插入 txn_map_ → 返回 txn_id
  - `commit(txn, log_manager)` — 断言 txn->state_ == GROWING → 写 COMMIT 日志到 WAL → **复制** lock_set_（因 unlock 内部 erase 会导致迭代器失效）→ 遍历副本调用 `lock_manager_->unlock(txn, lock_data_id)` 释放所有锁 → txn->state_ = COMMITTED → 保留在 txn_map_（不 erase，以便 SetTransaction 检测状态并创建新事务）
  - `abort(txn, log_manager)` — 断言 txn->state_ == GROWING → 逆序遍历 `txn->write_set_`（从最后一个 WriteRecord 往前）→ 根据 WType 分支回滚（DELETE_TUPLE→insert 恢复、INSERT_TUPLE→delete 撤销、UPDATE_TUPLE→delete+insert 恢复）→ 写 ABORT 日志 → 复制 lock_set_ → 遍历副本释放所有锁 → txn->state_ = ABORTED
- **Transaction 类**：
  - `txn_id_`：事务唯一标识（txn_id_t，从 TransactionManager 分配）
  - `state_`：TransactionState 枚举（DEFAULT / GROWING / COMMITTED / ABORTED）
  - `isolation_level_`：隔离级别（READ_COMMITTED / REPEATABLE_READ）
  - `lock_set_`：`std::unordered_set<LockDataId>`，记录该事务当前持有的所有锁
  - `write_set_`：`std::vector<WriteRecord*>`，按写操作执行顺序记录 undo 信息
  - 辅助方法：`get_lock_set()` / `append_write_record(WType, tab_name, rid, record)` / `get_write_records()`
- **WriteRecord 三种类型**：
  - `INSERT_TUPLE`：记录 {tab_name, rid} — abort 时 delete_record(rid)
  - `DELETE_TUPLE`：记录 {tab_name, rid, old_record} — abort 时 insert_record(rid, old_data) 恢复到原位置
  - `UPDATE_TUPLE`：当前实现已改用 DELETE_TUPLE + INSERT_TUPLE 双记录，避免单记录追踪 delete+insert 位置变化

## Page 23：2PL 集成实现要点（Lab4）
- **RmFileHandle 锁集成**（在 4 个 CRUD 方法中嵌入锁调用，通过 `context->lock_mgr_` 访问 LockManager）：
  - `get_record(rid)` → `lock_shared_on_record(txn, rid, fd)` 加行级 **S 锁**（事务读保护，防止脏读和不可重复读）
  - `insert_record(buf)` → 插入后 `lock_exclusive_on_record(txn, result_rid, fd)` 加行级 **X 锁**（新记录也需保护，防止其他事务脏读未提交插入）
  - `delete_record(rid)` → `lock_exclusive_on_record(txn, rid, fd)` 加行级 **X 锁**（写操作排他保护）
  - `update_record(rid, buf)` → `lock_exclusive_on_record(txn, rid, fd)` 加行级 **X 锁**（写操作排他保护）
  - 所有锁调用前检查 `context != nullptr && context->txn_ != nullptr`（非事务模式跳过锁）
- **执行器 WriteSet 集成**（在 3 个写执行器中记录 undo 日志）：
  - `InsertExecutor::next()` → insert_record 后 → `txn->append_write_record(INSERT_TUPLE, tab_name_, rid_)`
  - `DeleteExecutor::next()` → 先 get_record 保存旧内容 → `txn->append_write_record(DELETE_TUPLE, tab_name_, rid, *old_record)` → 再 delete_record
  - `UpdateExecutor::next()` → 先 get_record 保存旧内容 → fh_->delete_record(old_rid) → `append_write_record(DELETE_TUPLE, tab_name_, old_rid, *old_record)` → fh_->insert_record(new_data) → `append_write_record(INSERT_TUPLE, tab_name_, new_rid)`
- **commit 关键 Bug 修复**：
  - **迭代器失效**：遍历 `lock_set_` 调 `unlock()` 时，unlock 内部调用 `lock_set_->erase()` → 迭代器失效 → segfault。修复：`auto lock_ids = *txn->get_lock_set()` 先拷贝，再遍历副本
  - **txn_map.erase 导致断言失败**：commit/abort 后从 txn_map_ 中 erase 事务 → rmdb.cpp 的 `SetTransaction` 再次调用 `get_transaction(old_txn_id)` → 断言 `txn_map.find(txn_id) != txn_map.end()` 失败 → 服务崩溃。修复：不 erase，保留 COMMITTED/ABORTED 状态的事务在 map 中，SetTransaction 检测到非 GROWING 状态时创建新事务
- **abort 关键 Bug 修复**：
  - **DELETE_TUPLE 回滚位置错误**：`fh->insert_record(buf)` 分配新槽位 → 后续 INSERT_TUPLE 的 undo（delete_record(old_rid)）删除的是错误位置 → 数据重复或丢失。修复：使用重载 `fh->insert_record(wr->GetRid(), wr->GetRecord().data)` 恢复到原始 rid
  - **UPDATE 回滚不完整**：单个 UPDATE_TUPLE WriteRecord 无法追踪 delete+insert 的 rid 变化（新记录可能分配到不同槽位）。修复：改为 DELETE_TUPLE + INSERT_TUPLE 双 WriteRecord，各自携带精确的 rid
- **锁升级检查**（保证写冲突正确检测）：
  - lock_exclusive_on_record 和 lock_exclusive_on_table 中，当事务已持有 S 锁请求升级为 X 时，不能直接升级 —— 必须先扫描队列检查是否有其他事务的 granted 锁。若有 → 抛出 DEADLOCK_PREVENTION → 触发 abort。这是保证 lost_update / unrepeatable_read 等并发测试通过的核心修复

## Page 26：Bug 分析与实验总结
- **Bug 发现方法论**：
  - 读测试源码 → 理解测试期望的行为（如"txn1 写后 txn2 读应该 abort"）→ 对比实际行为（实际返回了脏数据）→ 二分法缩小范围（在锁函数打断点，观察锁队列状态）→ 定位根因
  - gdb 断点调试：在 lock_manager.cpp 的锁函数、transaction_manager.cpp 的 commit/abort 打断点，逐步执行观察锁状态和事务状态变化
  - 日志打印：在加锁/解锁/提交/回滚路径打印 txn_id + 锁类型 + LockDataId 三元组，还原事件序列
- **各 Lab 典型 Bug 分类对比**：

| Lab | TODO 数 | 隐藏 Bug | 典型问题类型 |
|-----|---------|---------|------------|
| Lab1 | 24 | 0 | 框架代码完善，辅助函数完备，实现顺利 |
| Lab2 | 22 | 5 | 零初始化陷阱、pin 泄漏、边界条件、父结点更新遗漏、并发锁缺失 |
| Lab3 | ~15 | 0 | 火山模型标准化，写操作索引同步容易遗漏 |
| Lab4 | ~10 | 11 | 迭代器失效、锁升级检查、并发场景思维盲区、WriteSet 精确性、框架假设偏差 |

- **关键教训**：
  - **并发场景下只检查自己不够**：锁升级时必须检查所有并发事务的锁状态，否则写保护形同虚设 —— 这是 Lab4 最核心的教训
  - **遍历容器 + 修改容器 = 必崩**：C++ 中 `for (auto &x : set)` 循环内调用 erase → 迭代器失效 → undefined behavior。最简单的解：拷贝后遍历
  - **undo 信息必须精确到每条记录**：WriteRecord 不能只记录逻辑操作（"我做了 UPDATE"），必须记录物理位置（old_rid + new_rid），否则回滚时找不到数据
  - **框架代码可能暗藏假设**：如 LockMode 是 private 枚举（不能写 static helper）、SmManager 没有公开 get_rm_file_handle() → 需要灵活绕过而非死磕框架
  - **写代码前先读测试**：测试是最好的规格说明，理解测试期望能避免方向性错误
- **系统能力提升**：通过 RUCBase 四个实验，深入理解了数据库内核四层架构（存储→索引→执行→事务），掌握了 POSIX I/O、LRU 缓存、B+ 树算法、火山模型、2PL 并发控制等核心技术，积累了 46+ TODO 和 16+ Bug 的 C++ 工程调试经验
- **工程素养提升**：学会了"读测试 → 理解预期 → 对比行为 → 定位根因"的系统调试方法论，体会了并发 Bug 的隐蔽性和排查难度，认识到好的框架设计对实现效率的倍增效应
